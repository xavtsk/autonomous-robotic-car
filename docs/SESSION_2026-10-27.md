## 1. What changed (by file)

### Barcode calibration — the root cause of "barcode never read"
* `controller/builtin_calibration.h`: `S3_BUILTIN_CAL_BARCODE` changed from
  `{134,179,275,335}` (Gin, old paper/height) to **`{170,260,3250,3850}`**
  (white 170–260, bars 3250–3850 raw; midpoints 215/3550). Measured from the
  21:48 course run after the barcode sensor was moved and new paper used.
* `subsystem3/ir_bench_config.h` (Buddy 3's file): `IR_BENCH_WHITE_RAW 215`,
  `IR_BENCH_BLACK_RAW 3550`, kept in sync as `builtin_test.c` requires.
* Why it mattered: with black = 305 raw, every grey reading between bars
  (blurred white gaps, raw 300–1500) became darkness 1000, bars merged, and
  the decoder rejected everything. With the new references the 21:48 trace
  decodes at any fixed cut-off between raw 1000 and 3000.
* **These references are only valid for this paper, sensor height and
  lighting.** Gin's old-paper bars (~300 raw) read as white now. Recalibrate
  (GP20 hold 2 s, or update the table) if any of those change.

### Barcode-only black/white cut-offs
* `controller/course_profile.h`: `S3_BARCODE_WHITE_LIMIT` / `S3_BARCODE_BLACK_LIMIT`
  (now **400/600**, the normal values) applied in `s3_course_navigation()` to
  `cfg->calibration[S3_SENSOR_BARCODE]` only. Line sensors always keep 400/600.
  Limits survive calibration (`s3_calibration_finish()` only replaces raw refs).
* Briefly set to 650/700 as a workaround for the stale calibration; reverted.

### Barcode trace recorder + Wi-Fi delivery (diagnostic only)
* `controller/barcode_capture.{h,c}` (new), `controller/s3_integration.c`:
  records barcode-sensor samples during a run; after the run sends them over
  USB (if a terminal is open) and Wi-Fi.
* Episode start/end now follow the decoder's own decision: starts on surface
  BLACK, ends after 40 consecutive WHITE samples (was fixed darkness 250/120,
  which broke when white read ~557).
* `lib/liblwip/sysdepend/pico_rp2040/mqtt_utk.{h,c}`: topic
  `car/debug/barcode`, weak hook `mqtt_utk_debug_take()`, sent only when no
  telemetry is waiting. Upload takes ~5–20 s; **a new START cuts it off**.
* `tools/buddy1_live.py`: shows `car/debug/*` lines and saves
  `barcode_trace_YYYYmmdd_HHMMSS.txt` (from `[BCAP] run summary` to `[BCAP] end`).
* `.gitignore`: `barcode_trace_*.txt`.

Trace format (one sample = `raw:dark4:flags:mm:dt`):
* `raw` ADC 0–4095; `dark4` = darkness/4; `mm` travel since episode start
  (odometry); `dt` ms since previous sample.
* `flags`: bits 0–1 surface (1 white, 2 black); bits 2–4 decoder status
  (1 decoded, 2 rejected, 3 timing error, 4 overflow); bit 5 collecting;
  bit 6 rearming; bit 7 sample gap > 30 ms.
* 20 pre-trigger samples per episode, pool 2400 samples, max 12 episodes.
  A wide space (> 40 samples at slow speed) splits one barcode across two
  episodes; the white between episodes is not stored.
* Summary line counts (decoded/rejected/...) cover the whole run, including
  rejects that happen in unstored white.

### After-turn line search (new, simulator-tested only)
* `controller/s3_drive.{h,c}`: options `search_deg`, `search_mps`, `track_m`
  (defaults 0 = off, original behaviour). If the existing after-turn check
  fails (no front sensor touched the tape in the last 0.3 s of the spin), the
  car sweeps on the spot up to ±`search_deg` around where the spin ended —
  first toward the likely side (last touch in the 2nd half of the spin =
  overshoot → sweep back; otherwise keep turning), then back across — and
  resumes following when a front sensor touches. Not found → halt LINE_LOST.
  Time-based (angle → time via `track_m`, `search_mps`); state stays
  `S3_DRIVE_MANOEUVRE` with `searching` set (telemetry shows "turning").
* `course_profile.h`: `S3_TURN_SEARCH_DEG 35`, `S3_TURN_SEARCH_MPS 0.05`,
  `S3_TRACK_M 0.116`. Keep < 45° so it cannot reach a neighbouring arm.
* `testing/integration/course_sim.c`: new scenarios — spin ends at 63° and
  117° (LEFT and RIGHT) → search finds the line; advance 0 still halts.
  Simulator default sensor distance now = `S3_SENSOR_TO_AXLE_MM` (135);
  straight test time budget scales with cruise speed.
* `course_test.c`: option defaults/values/validation checks.

## 3. Barcode facts learned today

* Decoder (Buddy 3, `subsystem3/barcode_decoder.c`) is correct: all 26
  letters both directions + PDF fixtures pass. It works on **durations**:
  exactly 29 runs; 6 narrow + 3 wide per character; wide/narrow 1.8–3.5;
  each run within ±35 % of its class; `*` start/stop; quiet zone ≥ 10 narrow
  each side; narrow ≥ 30 ms (and ≥ 3 × sample gap); any run ≤ 1 s; whole
  barcode ≤ 10 s. Sampling is 10 ms (`S3_SAMPLE_PERIOD_MS`), which is ample.
* Speed limits for the current prints:
  * Z/F print: thin ≈ 6 mm, wide ≈ 18 mm, barcode ≈ 25 cm. At 0.03 m/s it took
    9.4–10 s and was rejected on the 10 s frame limit; at 0.04 it takes ~6.3 s
    and reads. Keep ≥ 0.035 m/s for this size (or raise `max_frame_us`).
  * Y print: about half that size; thin bars (~3 mm) are near the optical
    limit. Not read today (see §0).
* Slowing down does **not** help thin bars: the limit is the sensor's viewing
  spot (blur), not speed or sampling (bench test held still: thin bar never
  reached 600 at the old height).
* Sensor outputs: AO (analog, used now; yellow Grove wire to AO → GP28) and
  DO (module comparator, set by the blue knob, drives the module LED). The
  LED switching only proves the module's own comparator; the car reads AO
  through the calibration. DO was tried (clean 0/4095) but the knob was hard
  to centre; reverted to AO with the new calibration.
* Speed changes inside a barcode distort durations (wheels stalling, hand
  nudges, hard steering): the 22:14 run was rejected because the car stopped
  mid-barcode.
* "Rejected" means no letter at all, not "read but refused".

## 4. Run procedure (what works)

1. Build + flash course firmware:
   `make -C build_make CONSOLE=usb_cdc WIFI=cyw43 NET=lwip MQTT=1 TEST=0 IR_BENCH=0 S3_MOTION=1 DIAGNOSTICS=0 MOTION_SMOKE=0 -j8`
   → hold BOOTSEL, power on → `cp -X build_make/mtk3pico_smp1_usb_cdc_wifi_lwip_mqtt_s3_motion.uf2 /Volumes/RPI-RP2/`.
   If make says "Nothing to be done" after a header change, `touch`
   `app_program/controller/s3_integration.c vehicle_controller.c` first.
2. Mac on the iPhone hotspot (Mac 172.20.10.2, car .3). Keep the iPhone's
   Personal Hotspot screen open while the car joins (new devices cannot join
   otherwise). Tab 1 `mosquitto -c mosquitto-dev.conf -v`; tab 2
   `mosquitto_sub -h 172.20.10.2 -t '#' -F '%t %x' | python3 tools/buddy1_live.py`.
3. Wait for `STATE stopped` in tab 2, then send the letter list, e.g.
   `python3 tools/buddy1_mqtt_codec.py encode-map --forward A --left Z --right Y --uturn C | xxd -r -p | mosquitto_pub -h 172.20.10.2 -t car/cmd/barcode_map -s`.
   Wait for `REPLY OK`. The list is erased by every flash/power cycle and
   locks at the first START (`BUSY` until the next power cycle).
4. START; after the run wait for `[BCAP] end` before the next START.

Bench (no motors, no Wi-Fi): `WIFI=none NET=none MQTT=0 IR_BENCH=1 IR_CHANNELS=3 S3_MOTION=0`
→ `..._ir_bench_3sensor.uf2`, read with `screen /dev/tty.usbmodemMTK3PICO1 115200`.
It ignores the course-profile cut-offs.
